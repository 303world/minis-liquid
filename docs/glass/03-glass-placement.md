# 玻璃使用规范（哪里用、哪里绝对不用）

> 依据：iOS 端**全项目只有 9 处** `glassEffect`，其余全是普通材质或纯色。
> 玻璃的价值来自"稀缺" —— 一旦到处都是，它就退化成半透明灰卡片，还顺带把帧率吃光。
> 所以本项目采用**白名单制**：不在名单里的表面，一律不许玻璃。

---

## 一、三条硬原则

1. **只给「浮在内容之上的壳」上玻璃。**
   顶栏、输入条、FAB、Sheet、菜单、弹窗 —— 它们的共同点是"内容会从下面滚过去"。
   内容本身（消息气泡、列表行、卡片、代码块）一律不玻璃。

2. **一屏最多 6 块玻璃，玻璃面积总和 ≤ 屏面积 25%。**
   这两条同时是性能约束和审美约束。超了就自动降档（见 §5）。

3. **背后没有内容可采样的，不给玻璃。**
   纯色页上的玻璃只会采到同一个颜色，模糊等于没做，还白烧 GPU。
   这类页面靠 `GlassWallpaper`（极淡层叠渐变）提供可采样的层次，或者干脆不玻璃。

## 三、黑名单（永不玻璃，写进 code review 检查项）

| 禁止对象 | 原因 |
|---|---|
| **消息列表的每一条气泡 / 工具卡** | `LazyColumn` 逐项玻璃 = 每帧录制 N 次，直接掉到 10fps |
| **设置页的每一行 / 每个分组卡** | 一屏能出现 10+ 个元素，破 §一.2 的两条约束 |
| **用户消息气泡** | iOS 是玻璃（r18），但安卓上气泡数以十计；改用现有实色气泡，差异记入本文档（见下） |
| 终端 / WebView / 文件预览的内容区 | 原生 View，Compose 采样不到，只会糊一张"玻璃窗贴纸" |
| Markdown 代码块、表格 | 内容需要锐利可读 |
| 输入框内部的每个按钮 | 玻璃套玻璃，iOS 自己都否决了（`buttonStyle(.glass)` 使用数 = 0） |
| 任何 `Popup` / `DropdownMenu` 内的第二层 | 同上 |

---

## 四、已知与 iOS 的差异（主动放弃，不是漏做）

| 项 | iOS | 本项目 | 原因 |
|---|---|---|---|
| 用户消息气泡 | 玻璃 r18 | 实色 | 数量多，逐条采样不划算 |
| 玻璃 morph（FAB ↔ 搜索条） | 有 | 不做 | 需要 `SharedTransitionLayout`，成本高、收益小 |
| 玻璃随系统"减少透明度"退化 | 系统自动 | 自己接 | 安卓没这层系统联动 |

## 五、降级与开关

| 条件 | 行为 |
|---|---|
| API < 31 | Off：纯半透明（观感 = 上游） |
| API 31~32 | Lite：只有模糊，无折射 |
| 滚动进行中 | 降一档，停稳 120ms 恢复（滚动时重采样最贵） |
| 连续 3 帧超 16ms | 本页降档，直到下次进入 |
| 系统动画时长为 0 / 用户关玻璃 | Off |
| 用户设置 | 关 / 标准 / 高（只能 ≤ 设备上限） |

## 六、性能预算（每条都要在真机上验）

| 指标 | 预算 |
|---|---|
| 每屏 backdrop 份数 | **1**（绝不允许每元素一份） |
| 同屏玻璃元素 | ≤ 6 |
| 玻璃面积总和 | ≤ 屏面积 25% |
| 聊天页滚动 | P95 ≤ 16ms |
| Sheet 弹出 | ≤ 250ms 完全展开 |
| 冷启动增量 | ≤ 150ms |
| 内存增量 | ≤ 24MB |

---

## 七、落地顺序（每一屏都要单独出包验收）

1. `GlassWallpaper`（背景层，无它则一切都是灰卡）
2. 会话列表：顶栏 → FAB
3. 聊天页：顶栏 → 输入条（重写自绘）→ 工具状态条
4. 浮层收敛：`MinisSheet` → `MinisAlertDialog` → `MinisMenu`
5. P1 的四项
6. 性能档位与设置项

> 每一步都单独提交、单独出包，出问题能立刻定位到是"哪一屏的哪块玻璃"。
